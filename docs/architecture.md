# Архитектура модуля

## Сопоставление с кодом команды

| Референс saq-prof-control-demo | Модуль возражений |
|---|---|
| frontend/src/modules/prof/ProfControlModule.tsx | frontend/src/modules/objections/ObjectionsModule.tsx |
| pages/CasesList.tsx и CaseWorkspace.tsx | страницы реестра и карточки с теми же именами |

| backend/apps/.../services | в текущем прототипе — чистые frontend-сервисы; серверная реализация впереди |

## Границы ответственности

React-компоненты отображают данные и собирают значения форм. `formDefinitions.ts` описывает поля, зависимости и пояснения. `services/workflow.ts` проверяет роль, этап, обязательные данные и выполняет одно действие над копией состояния. Ошибка не изменяет исходные данные. `services/deadlines.ts` рассчитывает сроки; `services/decisions.ts` — результаты по пунктам и голосование. Модель сохраняет успешную транзакцию через интерфейс `ObjectionsRepository`.

Ключ демо-хранилища сохранён: `saq.objections.demo.v1`, поэтому исходные данные предыдущего прототипа доступны после обновления. Репозиторий перед сохранением получает целое состояние; объём рассчитан на демонстрационные дела. Для рабочего многопользовательского режима это необходимо заменить серверными операциями с проверкой версии и прав.

## Дальнейшая интеграция

При подключении к Django/DRF предметные проверки должны выполняться сервером, а роли определяться аутентифицированным пользователем. Нужны сущности обращения, пункта, заседания, голоса, версии документа, события доставки и журнала. Доказательство вручения не должно заменяться отметкой об отправке. Вложения хранятся отдельно, а не в JSON карточки. Локальный демо-переключатель роли не является механизмом доступа.

Реальные контракты API и модели backend здесь не объявлены реализованными. Предлагаемая граница frontend-адаптера позволяет подключить их после согласования с разработчиками.
